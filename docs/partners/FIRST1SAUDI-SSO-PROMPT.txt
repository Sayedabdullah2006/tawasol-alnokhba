1. رحلة الدخول والتسجيل
أضف مسار start خادميًا للدخول الموحد. استخدم مكتبة openid-client@6.8.9 المرجعية المرفقة مع Node 22 أو أحدث. ملفات sso-runtime تحتوي package.json وlock؛ ثبّت الاعتماد داخل مجلد runtime خاص بالخادم. يمكن استخدام oidc-bridge.mjs عبر stdin/stdout بين PHP وNode، دون تمرير أسرار في command line أو تسجيل خرج العملية؛ الخرج الناجح قد يحتوي رموزًا سرية.

begin() يعيد authorization_url وtransaction خاصًا بالخادم. احفظ transaction مرتبطًا بجلسة المتصفح ووجهة عودة محلية آمنة، ثم وجّه العميل إلى authorization_url. أنشئ state وnonce وPKCE verifier جديدة لكل محاولة. لا تحفظ verifier أو الرموز في localStorage أو Query String.

لزر «إنشاء حساب» استخدم begin({screen:'register'}). التسجيل يحدث في الحسابات المركزية، مع تأكيد البريد برمز؛ لا تنشئ كلمة مرور ثانية في WordPress. لربط حساب قديم أو تبديل الحساب استخدم begin({forceLogin:true}) لإثبات الحساب المركزي الذي يقصده العميل.

صفحات المصادقة المركزية تظهر بهوية أول سعودي وخط Almarai وألوانه، ثم تعيد العميل إلى callback المسجل. أبقِ صفحات البداية والعودة والتنبيهات داخل أول سعودي بهويته الحالية.

2. معالجة callback بأمان
أنشئ المسار المسجل دون تحويل تلقائي للمضيف أو إضافة slash يفقد التطابق. callback يُعالج في الخادم ثم يعيد العميل إلى رابط نظيف داخل أول سعودي.

تحقق من transaction الأصلية المرتبطة بالمتصفح، ولا تقبل state أو verifier من جسم طلب يختاره المستخدم. استهلك transaction مرة واحدة ذريًا قبل استدعاء finish(callbackUrl,transaction)، وصلاحيتها لا تتجاوز خمس دقائق. احمِ التدفق من login CSRF وإعادة الاستخدام وتثبيت الجلسة.

المكتبة المرجعية تتحقق من توقيع ID token وissuer وaudience وnonce وstate وPKCE وUserInfo subject. لا تستبدلها بفك JWT دون تحقق، ولا تستخدم البريد وحده كمعرّف هوية.

3. التحقق المركزي بعد OIDC
بعد تبادل الكود، وقبل إنشاء جلسة WordPress موثقة، استدعِ من الخادم:
POST https://nukhba.media/api/partners/v1/identity/session
بنفس HMAC الحالي، partner awwal-saudi، وnonce جديد، ومفتاح POST مناسب.
الجسم فقط: {"access_token":"رمز OAuth access token"}

لا تستخدم ID token أو رمز Supabase أصليًا من تسجيل دخول محلي بديلًا عن رمز OAuth. لا ترسل subject أو user_id أو email أو role أو customer_id داخل هذا الجسم.

إذا لم يُعرف العميل المحلي بعد، استعمل X-Customer-ID موقّعًا بقيمة oidc.<subject> للتحقق والاستعلام فقط. يسترجع المسار subject وissuer والبريد المؤكد والملف الشخصي وlink إن كان الربط موجودًا. لا يصدر صلاحيات WordPress أو دورًا إداريًا.

المسار يتحقق من صلاحية الجلسة المركزية وإلغائها ومن هوية التطبيق. عند 401 لا تُنشئ جلسة محلية ولا تستخدم تطابق البريد كبديل؛ جدّد الرمز أو أعد الدخول. عند 503 اعرض إعادة المحاولة دون منح وصول غير متحقق.

4. ربط الحسابات الحالية دون فقدان بيانات
استخدم (issuer,subject) معرّف الهوية، مع جدول WordPress ذي قيود uniqueness فعلية. لا تعتمد على usermeta قابلة للتعديل وحدها لحماية الربط.

السيناريوهات:
أ) subject مرتبط مسبقًا: سجّل دخول المستخدم المحلي المرتبط بعد التحقق، وأبقِ customer ID الأصلي.
ب) عميل لديه حساب WordPress قديم غير مرتبط: يثبت دخوله إلى الحساب القديم، ثم يسجل دخولًا مركزيًا حديثًا، ثم يرى شاشة تأكيد واضحة بالحسابين قبل الربط.
ج) البريد نفسه موجود محليًا دون ربط subject: لا تدمج أو تسجل دخول ذلك الحساب تلقائيًا. اطلب إثبات الحساب القديم أو الاستعادة.
د) مستخدم مركزي جديد بلا حساب محلي متعارض: أنشئ سجل عميل محليًا بصلاحية customer/subscriber ثابتة، دون نسخ كلمة المرور، واحصل على f1o_customer_id() الثابت ثم اربطه.

للتثبيت استدعِ:
POST https://nukhba.media/api/partners/v1/identity/link
الجسم فقط {"access_token":"..."}، وX-Customer-ID هو f1o_customer_id() للحساب المحلي الذي ثبتت ملكيته، مأخوذ من الخادم. لا تقبل معرف حساب الربط من المتصفح.

الاستجابة تحتوي subject وexternal_customer_id وlinked_at وlinked_orders. الربط ذري وقابل لإعادة المحاولة بأمان. يحفظ المعرفات الخارجية، ويربط الطلبات المطابقة غير المرتبطة بالحساب المركزي، ويجعل الطلبات الجديدة مرتبطة به تلقائيًا.

عند 409 IDENTITY_LINK_CONFLICT لا تغيّر المعرف ولا تجرب ربط حساب آخر تلقائيًا؛ اعرض مراجعة الدعم. لا تنقل طلبات أو فواتير اعتمادًا على تشابه الاسم أو البريد أو الجوال.

احتفظ بكل حسابات WordPress وأدوارها وكلمات مرورها القديمة وخيارات f1o_identity_<user_id>. لا تنفذ ترحيلًا جماعيًا أو حذفًا أو إعادة تعيين كلمات مرور. ربط الحسابات القديمة تدريجي بعد الإثبات. أبقِ دخول إدارة WordPress واستعادتها الحاليين أثناء الإطلاق.

5. حفظ الجلسات وتجديدها والخروج
بعد التحقق، أنشئ/جدّد كوكي WordPress آمنة Secure وHttpOnly وSameSite مناسبة للعودة عبر GET، وغيّر جلسة المصادقة لمنع session fixation.

خزّن access/refresh tokens مشفرة داخل الخادم ولكل جلسة WordPress مستقلة، وليس ملفًا عامًا أو localStorage أو خيارًا مكشوفًا أو سجلًا واحدًا مشتركًا لكل أجهزة المستخدم. لا تسجل بيانات callback أو أكوادها أو رموزها أو client secret.

جدّد الرموز عبر refresh(refreshToken,subject) مع قفل لكل جلسة لمنع سباق refresh-token rotation، وتأكد من بقاء subject نفسه. تحقق من identity/session قبل العمليات المحمية؛ أي كاش للتحقق لا يتجاوز 30 ثانية ويرتبط بالجلسة، ويُلغى فور الخروج أو رفض الهوية.

للخروج من جلسة أول سعودي استدعِ من الخادم، متى كان الرمز صالحًا:
POST https://nukhba.media/api/partners/v1/identity/logout
الجسم {"access_token":"..."}.
ثم امسح جلسة WordPress ورموزها والمعاملات المعلقة والكاش. المسار يلغي جلسة OAuth الحالية فقط. لا تعلن تسجيل الخروج من كل المواقع أو الأجهزة؛ جلسة تواصل النخبة الأصلية مستقلة. إذا انتهى الرمز جدّده للخروج إن أمكن، وامسح الجلسة المحلية دائمًا.

6. الحفاظ على الصلاحيات والربط التجاري
لا تمنح WordPress admin/editor بناءً على claims أو اسم أو بريد أو دور مركزي. الحساب الجديد له دور العميل الثابت؛ الأدوار القديمة تبقى كما هي بعد إثبات الربط، دون ترقية تلقائية.

استخدم external_customer_id المرتبط نفسه في جميع استدعاءات الباقات والطلبات والملفات والمراجعة والدفع والفواتير. لا تستبدل wp.UUID بالـsubject في طلبات التاريخ القديم.

أضف identity إلى قائمة مسارات العميل الخادمي المسموحة عند الحاجة، لكن لا تجعل استدعاءاتها العامة تقبل OAuth token من المتصفح؛ callback والخادم يديران الرموز. حالة OTP المحلية أو بريد يرسله المستخدم ليست بديلًا عن المصادقة المركزية.

رموز OAuth لا تُستخدم للوصول المباشر إلى Supabase Database أو Storage؛ هذه المسارات محجوبة لهذا التطبيق. البيانات التجارية تبقى عبر API الشريك الموقّع. طلبات قناة أول سعودي تبقى مفلترة بقناتها؛ توحيد الحساب لا يمنح الموقع تلقائيًا جميع بيانات قنوات أخرى.

حافظ على ميسر وحساب البائع وصفحة عودة الدفع والكتالوج الديناميكي والحالات والفواتير كما تعمل. لا تغير استحقاقات العضويات أو تنشئ اشتراكًا مدفوعًا لمجرد التسجيل. افصل هوية OAuth عن أي إعداد Sandbox للدفع؛ مسارات الهوية تستخدم العميل الرئيسي awwal-saudi.

7. الاختبارات والتسليم
اختبر في بيئة معزولة أو حسابات اختبار واضحة:
- مستخدم مركزي موجود يدخل دون إنشاء حساب مركزي آخر.
- مستخدم جديد يسجل ويؤكد البريد.
- حساب WordPress قديم يربط بعد إثبات الحسابين وتبقى طلباته وفواتيره ومعرف العميل.
- نفس البريد دون ربط لا يسبب دمجًا تلقائيًا.
- منع ربط الهوية بحساب آخر أو الاستيلاء على طلباته.
- رفض state/nonce/PKCE أو issuer/audience/signature الخاطئة، والكود المعاد أو المنتهي، وعناوين العودة غير المسجلة.
- تجديد الجلسة دون تغير المستخدم، وخروج أول سعودي دون إلغاء الجلسة الأصلية في تواصل النخبة.
- رفض جلسة مركزية ملغاة، وعدم تخزين الرموز أو أسرارها في الواجهة والسجلات.
- بقاء أدوار WordPress القديمة ودخول الإدارة، وعدم منح صلاحيات جديدة من claims.
- استمرار رحلة الطلب والدفع التجريبي والمراجعة والفاتورة بعد الدخول.
- الكمبيوتر والجوال وعدم وجود تحويلات دائرية.

لا تختبر بتغيير كلمات مرور أو ملكية حسابات العملاء الفعلية، ولا تُجرِ خصمًا فعليًا. أعطني نتائج الاختبارات، وما لم يُختبر، وأي إعداد ناقص قبل إعلان اكتمال الطرفين. طرف تواصل النخبة مجهّز؛ اكتمال الدخول من أول سعودي يتطلب تطبيق هذه الخطوات في خادمه وواجهته.
