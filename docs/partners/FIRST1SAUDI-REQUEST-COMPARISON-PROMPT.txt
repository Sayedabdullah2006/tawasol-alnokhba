نفّذ تحديث صفحة إنشاء الطلب في أول سعودي لتتبع ترتيب تواصل النخبة الجديد، بهوية أول سعودي وألوانه وخطوطه، مع الحفاظ على الربط والدخول الموحد والطلبات والدفع والفواتير الحالية. هذا التوجيه يستبدل ترتيب الخطوات السابق الذي يضع المحتوى قبل الباقة، ولا يغيّر عقد API الحالي.

المراجع المرفقة: openapi.json بالإصدار 1.6.0، وDYNAMIC-CATALOG.md، وFIRST1SAUDI-ORGANIZATIONS-PROMPT.txt، وFIRST1SAUDI-STATE-PROMPT.txt، وFIRST1SAUDI-INVOICE-PROMPT.txt. مكوّن PackageComparison وملف تنسيقه مرجع للسلوك فقط؛ طبّقه ضمن بنية أول سعودي وهويته، دون نسخ غلاف تواصل النخبة أو ألوانه. النتائج المرفقة تخص اختبار واجهة تواصل النخبة ولا تغني عن اختبار أول سعودي.

1) ترتيب الصفحة
الصفة ← نوع الخبر ← الباقة والقنوات للأفراد فقط ← تفاصيل الخبر والمرفقات ← المراجعة ثم الإرسال/الدفع بحسب المسار المركزي.
لا تعرض الباقات بشكل عام قبل تحديد الصفة ونوع الخبر، ولا تضف صفحة استعراض عامة أو بطاقات «تبدأ من» لهذه الرحلة.

الخطوة الأولى: الصفة «فرد، شركة/مؤسسة، جهة حكومية» من client_types. اعرض organization_fields للجهات بحسب الكتالوج، ومنها اسم الجهة الإلزامي واسم الممثل والسجل/الترخيص وفق التعريف المركزي. لا تحوّل الجهة إلى فرد لتجاوز التسعير اليدوي.
الخطوة الثانية: أنواع الأخبار والتفريعات من categories_by_client_type وsub_options، مع التقيد بـ category_ids وrequest_types وقدرات الربط. الربط الحالي يدعم single؛ لا تضف إرسال الحملات أو استخدام رصيد العضوية لأن وجودهما في الواجهة الأصلية لا يعني دعمهما في API الشريك.
امنع الانتقال لخطوة لاحقة قبل اكتمال ما يلزمها، واسمح بالرجوع لتعديل الاختيارات. الروابط العميقة قد تملأ الاختيارات مسبقًا، لكنها تبدأ بتأكيد الصفة.

2) مقارنة باقات الأفراد
بعد الصفة ونوع الخبر، اعرض الباقات المؤهلة فقط بترتيب packages في الكتالوج. احترم required_category؛ الباقة المهنية تظهر عند فئتها المناسبة فقط، ولا تغيّر نوع الخبر تلقائيًا عند الضغط على باقة.
على الكمبيوتر: جدول واحد بعرض المساحة المتاحة، عمود للمزايا وأعمدة للباقات، أسماء وأسعار واضحة وزر اختيار لكل باقة، مع إبراز المختارة. الميزة المشمولة تعرض ✓ ومعها القيمة الفعلية؛ غير المشمولة تعرض × بلون محايد ومعنى نصي لقارئ الشاشة. لا تعتمد على اللون وحده.
اقرأ أسماء المزايا وقيمها وincluded وquantity إن وجدت من benefits، دون إعادة كتابة المزايا أو اختراع وعود أو شارة «الأكثر طلبًا». يمكن عرض مقارنة مختصرة مع زر «عرض جميع المزايا»؛ لا تُخفِ مزايا الشراء نهائيًا. استخدم النصوص الآمنة دون حقن HTML.
على الجوال: تبويبات/بطاقات مريحة للقراءة وزر لعرض جدول المقارنة، بتمرير أفقي داخل الجدول وعمود المزايا ثابت؛ لا يحدث تمرير أفقي للصفحة كلها. حافظ على لوحة المفاتيح وتسميات الحقول والتباين الواضح. لا تغيّر المزايا والأسعار الموجودة مركزيًا.
القنوات: إذا channels مصفوفة فهي القنوات المحددة؛ إذا null يختار العميل channel_count قنوات مختلفة من قنوات الناشر المتاحة. لا تسمح بقناة مكررة أو باقة لا يستطيع الناشر تنفيذ قنواتها، ولا تنتقل للتفاصيل قبل اكتمال الاختيار.

3) السعر الديناميكي وإعادة التسعير
المصدر الوحيد GET /catalog من خادم أول سعودي إلى https://nukhba.media/api/partners/v1 بالتوقيع الحالي. التزم بـ cache_ttl_seconds وحدّث الكتالوج عند فتح الرحلة والعودة إليها. لا تثبّت أرقام الأسعار أو أسماء الباقات أو أعداد القنوات في الكود، ولا تعتبر starts_from سعرًا نهائيًا.
كل مبالغ API بالهللات؛ حوّلها للريال للعرض فقط. بعد اختيار مدخلات التسعير والقنوات استخدم POST /quotes مع catalog_version للحصول على السعر المركزي، ولا ترسل سعر المتصفح كمرجع. لا تستخدم معادلة محلية بديلة للتسعير النهائي.
أعد التسعير عند تغيير نوع الخبر أو تفريعه أو الباقة أو الناشر أو القنوات أو الإضافات أو أي مدخل سعر يدعمه العقد. عند تغيير الصفة امسح الاختيارات غير المتوافقة وعرض السعر القديم، مع حفظ نص العميل ومرفقاته الخاصة قدر الإمكان ودون نقل ملكيتها.
عطّل المتابعة أثناء الحساب، وتجاهل الاستجابة المتأخرة لاختيار قديم. اعرض الإجمالي المفصل قبل التأكيد، ولا تضاعف تكلفة included_extras أو ميزانية إعلان مشمولة.
عند 409 CATALOG_CHANGED اجلب الكتالوج مجددًا واعرض السعر والمزايا للمراجعة؛ لا تؤكد شراء تلقائيًا بسعر تغيّر. عند فشل القراءة أو التسعير اعرض إعادة المحاولة دون تأكيد من سعر ثابت بديل. الطلبات السابقة تعرض package_snapshot المحفوظة؛ إذا كانت benefits القديمة null استخدم features المحفوظة.

4) التفاصيل والجهات
بعد الباقة اعرض حقول المحتوى من content_requirements وحقول career_fields عند انطباقها، ثم المرفقات الخاصة. حافظ على الرفع القائم ومسارات الملفات وملكية العميل، ولا تنشئ مسارًا غير موجود في العقد بغرض الرفع المبكر.
الشركة والجهة الحكومية تتجاوزان مقارنة الباقات وأسعار الأفراد إلى التفاصيل، مع اختيار قنوات الناشر وفق العقد. زر الإجراء «إرسال الطلب للمراجعة»، دون سعر ثابت أو دفع فوري. أنشئ POST /orders بصفة الجهة وبياناتها دون quote_id أو package_id أو سعر يحدده المتصفح؛ amount=null يعني «لم يُسعّر بعد».
حافظ على مسار العرض المالي المركزي القائم: GET /orders/{id}/offer، والمعاينة والقبول والرفض والتفاوض عبر POST على المسار نفسه، مع offer_revision وIdempotency. بعد القبول استخدم checkout فقط عندما ready_for_payment=true. العرض المجاني لا يولّد دفعًا مصطنعًا. بعد الدفع يعرض العرض للقراءة وفق can_decide، مع معالجة العرض المتغير أو المنتهي كما في العقد.

5) الحفاظ على الربط
كل اتصال مركزي من الخادم فقط. احتفظ بـ HMAC وnonce جديد لكل محاولة وX-Customer-ID من الجلسة الموثقة، وبمفتاح Idempotency نفسه والجسم نفسه لإعادة العملية نفسها، ومفتاح جديد لعملية مختلفة. لا تطبع الأسرار ولا تضعها في JavaScript أو Git.
لا تغيّر الحسابات أو ملكية الطلبات أو الدخول الموحد أو السجل السابق. حافظ على الملفات الخاصة واستكمال البيانات ومراجعة النص والتصاميم وطلب التعديل والاعتماد والمخرجات كما تعمل حاليًا.
اعرض حالات الطلب والدفع وتسمياتها كما يعيدها المصدر المركزي وstatus_definitions ومسار GET /orders/{id}/state؛ لا تختزلها أو تستنتج «مدفوع/مكتمل» محليًا. تأكيد السداد خادمي ولا يعتمد على معاملات رابط العودة.
احتفظ بـ checkout المركزي عبر ميسر، والبائع شركة تواصل النخبة، والعودة https://first1saudi.net/services/orders/return، وتنزيل الفاتورة الأصلية مع صلاحياتها. لا تستبدلها بفاتورة يصنعها أول سعودي.
لا تغيّر مفاتيح الدفع الحي أو الوضع العام، ولا تفتح الشراء العام. الاختبار عبر شريك Sandbox المعزول الصالح فقط. إذا انتهت صلاحيته اطلب تجديده؛ لا ترجع إلى live. لا خصم حقيقي ولا إصدار فاتورة إنتاجية للاختبار.

6) اختبارات القبول قبل التسليم
اختبر الصفات الثلاث، والفئات والتفريعات المناسبة، وأهلية الباقة المهنية وحقولها، وتغيير الاختيارات وإعادة التسعير، وصحة عدد القنوات ومنع تكرارها، والجدول والبطاقات بعروض 1440 و768 و390 دون تجاوز عرض الصفحة.
اختبر الأسعار والمزايا من API، وتغير الكتالوج والتعامل مع 409 دون شراء تلقائي، وبقاء الطلب القديم ببياناته المحفوظة. لا تنشر كتالوجًا تجريبيًا فوق الكتالوج الحي لمجرد الاختبار؛ استخدم بيانات معزولة أو محاكاة عقد واضحة لهذه الحالة.
بعميلين في Sandbox: إنشاء الطلب وإعادة المحاولة دون تكرار، وعروض الجهات، والملفات الخاصة، والمراجعات والاعتماد، وحالات الطلب والسداد، ونجاح ميسر TEST مع 3DS والرفض وصفحة العودة، والفاتورة الأصلية المعزولة، ومنع الوصول المتبادل إلى الطلب وstate والملفات والفاتورة.
سلّم نتائج موثقة وما لم يُختبر، مع تأكيد بقاء الشراء العام مغلقًا. لا تعتبر نجاح اختبارات واجهة تواصل النخبة دليلًا على نجاح اختبار أول سعودي أو ميسر في نسخته. قرار إطلاق الشراء منفصل بعد القبول.
