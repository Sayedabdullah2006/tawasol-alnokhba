تم تنفيذ دعم الشركة / المؤسسة والجهة الحكومية في API تواصل النخبة. طبّق الربط التالي في أول سعودي مع الإبقاء على هويته، والحسابات والدخول الموحد والطلبات والدفع والفواتير الحالية. لا تفتح الشراء العام؛ أكمل الاختبار عبر شريك Sandbox المعزول الحالي.

اقرأ openapi.json بالإصدار 1.6.0 ونتائج الاختبارات المرفقة. العنوان والبروتوكول والأسرار الحالية لم تتغير:
https://nukhba.media/api/partners/v1
جميع الاتصالات خادمية بتوقيع HMAC وX-Customer-ID ثابت من الحساب الموثق، وnonce جديد لكل محاولة. استخدم Idempotency-Key ثابتًا عند إعادة محاولة العملية نفسها، ومفتاحًا جديدًا لقرار جديد.

1. الواجهة وتسلسل الطلب
أزل الاستعراض العام للباقات وبطاقات «تبدأ من». ابدأ بالصفة ونوع الخبر، ثم المحتوى والمرفقات، ثم الباقات للأفراد فقط، ثم المراجعة والإرسال أو الدفع بحسب المسار المركزي.

GET /catalog أصبح يعيد إضافيًا:
- client_types: individual / business / government، مع الاسم العربي وpricing_mode وpackage_selection وrequest_types وcategory_ids وorganization_fields.
- categories_by_client_type: أنواع الأخبار المناسبة لكل صفة.
- content_requirements: شروط المحتوى العامة والخاصة بالفئة والشروط المعتمدة مركزيًا.
- request_types: الأنواع المدعومة حاليًا في الربط.
تبقى packages وextras وcategories وsub_options وstatus_definitions الحالية متاحة ومتوافقة مع الربط السابق. categories القديمة تخص الأفراد؛ استخدم categories_by_client_type عند اختيار الصفة.

اعتمد هذه البيانات ديناميكيًا. الربط الحالي يدعم single فقط؛ لا تعرض حملة قابلة للإرسال عبره.

للأفراد: أبقِ مسار quotes ثم orders ثم checkout القائم، وأعد التسعير عند تغيير ما يؤثر فيه. لا تستخدم starts_from كسعر نهائي.

للشركة والجهة الحكومية: لا تعرض باقات الأفراد أو تسعيرها أو دفعًا فوريًا. الإجراء الأول «إرسال الطلب للمراجعة». لا تحول الصفة إلى individual.

2. بيانات الجهة
اعرض حقول organization_fields حسب تعريف الكتالوج، وهي حاليًا:
org_name: اسم الجهة، إلزامي.
org_representative: اسم ممثل الجهة، اختياري.
org_license: السجل أو الترخيص، اختياري.
بالإضافة إلى بيانات التواصل المعتادة للمستخدم.

أنواع الأخبار الحالية للشركة: appointment وproduct.
أنواع الأخبار الحالية للجهة الحكومية: appointment وgovernment.
هذه أمثلة من المصدر الحالي؛ دع الواجهة تقرؤها من API ولا تثبتها في الكود.

3. إنشاء طلب الجهة
أرسل POST /orders بالصيغة التالية، دون quote_id أو package_id أو سعر:
{
  "client_type": "business",
  "request_type": "single",
  "influencer_id": "معرف ناشر متاح من الكتالوج",
  "category": "product",
  "org_name": "اسم الشركة أو المؤسسة",
  "org_representative": "اسم الممثل إن وجد",
  "org_license": "رقم السجل أو الترخيص إن وجد",
  "channels": ["x"],
  "title": "عنوان الخبر",
  "content": "نص الخبر",
  "customer": {
    "name": "اسم جهة الاتصال",
    "email": "البريد",
    "phone": "الجوال",
    "city": "المدينة",
    "handle": "حساب X إن وجد"
  }
}

للجهة الحكومية استخدم client_type=government ونوع خبر متاح لها، مع بقية بياناتها.
يمكن إرسال link وhashtags وpreferred_date بصيغة YYYY-MM-DD عند الحاجة.
اختيار قناة واحدة على الأقل مطلوب، ومن القنوات المتاحة للناشر فقط، دون تكرار.

الاستجابة الأولى تحتوي id وrequest_number وstatus=pending وamount=null وpricing_mode=manual وreplayed.
null يعني «لم يُسعّر بعد»، ولا تعرضه على أنه صفر أو خدمة مجانية.
لا ترسل status أو user_id أو payment_status أو admin_quoted_price أو final_total أو خصمًا أو إضافات مدفوعة عند إنشاء طلب الجهة. الإدارة تحدد العرض أولًا.

ارفع الوثائق والصور الخاصة بعد الحصول على معرف الطلب، باستخدام مسارات files وcomplete القائمة. أصبحت ملفات الجهات مسموحة أيضًا في pending وquoted وnegotiation. حافظ على رفعها داخل مسار الطلب وملكيته؛ لا تحول المستند الحكومي إلى رابط عام.

4. وصول عرض الإدارة
التسعير يتم من لوحة تواصل النخبة الحالية. تظهر الحالة quoted بعد إصدار العرض، ثم يتعامل العميل معه من أول سعودي.

GET /orders/{id}/state ما زال يعيد الحالات المركزية، وأضيفت إليه client_type وamount وquote_expires_at وoffer_available.
عند تغير الحالة أو المبلغ حدّث تفاصيل الطلب والعرض المالي.

أضف استدعاء:
GET /orders/{id}/offer

قبل التسعير يعيد available=false وamount=null.
عند وجود عرض يعيد can_decide وoffer_revision وbase_amount وamount وoffered_extras وselected_extras وexpires_at وexpired وnegotiation وcurrency وmoney_unit.
يبقى ملخص العرض ومبالغه متاحًا بعد الدفع أو إغلاق الطلب؛ اعرضه للقراءة فقط عندما can_decide=false، دون أزرار قبول أو تعديل أو تفاوض.

جميع مبالغ API الخارجية بالهللات؛ اقسم على 100 للعرض بالريال. النسب المئوية تبقى نسبًا وليست مبالغ.

اعرض الإضافات من offered_extras لهذا العرض، لا من أسعار يكتبها WordPress أو يختارها المتصفح. القيم مأخوذة من العرض المركزي أو مصدر الإضافات المركزي المعتمد.

5. معاينة العرض وقبوله ورفضه والتفاوض
المسار:
POST /orders/{id}/offer

معاينة السعر قبل التأكيد:
{
  "action": "preview",
  "offer_revision": "القيمة الحالية من GET offer",
  "selected_extras": ["معرف إضافة متاحة"],
  "discount_code": "كود الخصم إن وجد"
}
أرسل مصفوفة فارغة إذا لم توجد إضافات، واحذف discount_code إن لم يستخدمه العميل.
الاستجابة تحتوي base_amount وextras_amount وdiscount_amount وamount. المعاينة لا تعتمد العرض أو تستهلك كود الخصم.

للقبول أرسل البيانات نفسها مع action=accept ومفتاح Idempotency مستقل للقبول. لا ترسل السعر من المتصفح.
يعيد النظام status وamount وready_for_payment، ويحسب المبلغ والإضافات والخصم مركزيًا داخل معاملة تمنع تكرار الاستهلاك.
إذا ready_for_payment=true استخدم POST /orders/{id}/checkout القائم، ثم رحلة ميسر والعودة والتحقق الحالية دون تغيير.

إذا اعتمدت الإدارة عرضًا مجانيًا وصار الإجمالي صفرًا، فقد يعيد القبول status=in_progress وready_for_payment=false. لا تنشئ Checkout ولا تصطنع payment_status=paid ولا تعرض فاتورة مالية مدفوعة.

للرفض:
{"action":"reject","offer_revision":"...","reason":"سبب واضح لا يقل عن 10 أحرف"}
يعيد الحالة client_rejected كما في تواصل النخبة.

للتفاوض:
{"action":"negotiate","offer_revision":"...","reason":"سبب واضح لا يقل عن 10 أحرف","proposed_amount":90000}
proposed_amount اختياري وبالهللات، ولا يزيد على أساس العرض الحالي.
الخادم يطبق آلية التفاوض المركزية الحالية وحدود الجولات والحصة الشهرية. استخدم negotiation من GET offer ونتائج القرار لعرض المتاح؛ لا تحسب عرضًا بديلًا في WordPress.
بعد كل قرار أو تفاوض أعد جلب state وoffer. لا تعِد استعمال offer_revision القديمة لقرار جديد.

6. الأخطاء والتزامن
- OFFER_CHANGED: حدّث العرض وأعد عرضه للعميل قبل التأكيد، ولا تقبل سعرًا قديمًا بصمت.
- OFFER_EXPIRED: اطلب تجديد العرض من الإدارة.
- CHECKOUT_ACTIVE: لا تغيّر السعر أو تفتح محاولة دفع أخرى؛ حدّث حالة جلسة الدفع الحالية.
- NEGOTIATION_LIMIT: اعرض انتهاء الجولات أو الحصة وفق المعلومات المركزية.
- DISCOUNT_UNAVAILABLE: أعد المعاينة بعد توضيح مشكلة الكود.
- MANUAL_QUOTE_REQUIRED: هذه صفة تحتاج المراجعة؛ لا تعِد إرسالها كفرد.
- IDEMPOTENCY_CONFLICT: لا تغيّر محتوى العملية تحت المفتاح نفسه.
- ORDER_NOT_FOUND: لا تكشف بيانات طلب آخر أو تحاول معرف عميل بديلًا.

عند انتهاء الطلب شبكيًا، أعد العملية نفسها بالجسم والمفتاح نفسيهما مع nonce وتوقيع جديدين. حافظ على تعطيل التأكيد أثناء الحساب، وتجاهل استجابة المعاينة القديمة إذا تغير الاختيار.

7. الحفاظ على الربط والاختبار
لا تغيّر حالات الطلب والدفع أو تسمياتها محليًا. لا تستبدل سجل الطلبات القديمة أو معرفاتها، ولا تنقل ملكيتها اعتمادًا على البريد أو اسم الجهة. حافظ على الدخول الموحد، والأسرار الخادمية، والفواتير الأصلية والمراجعات والتصاميم والمخرجات.

اختبر في Sandbox بعميلين:
- الصفات الثلاث وأنواع الأخبار والحقول الخاصة بكل صفة.
- بقاء رحلة الأفراد وتسعيرهم كما تعمل.
- إنشاء شركة وجهة حكومية بحالة pending دون سعر أو دفع.
- إعادة المحاولة دون تكرار الطلب أو القرار أو استخدام الخصم.
- رفع وثائق خاصة قبل التسعير ومنع العميل الآخر من الوصول إليها.
- عرض الإدارة، ومعاينة الإضافات والخصم، والقبول والرفض والتفاوض.
- العرض المنتهي أو المتغير، وحدود التفاوض، ومنع تعديل السعر أثناء Checkout.
- العرض المجاني دون دفع مصطنع.
- ميسر TEST و3DS وصفحة العودة وحالة السداد والفاتورة الأصلية.
- الجوال والكمبيوتر، وعدم وجود عرض عام مستقل للباقات.

إعداد شريك Sandbox الخاص ما زال في الملف المحلي الآمن الذي تسلمتم موقعه سابقًا. لا تضعوه في ملفات الموقع العامة أو السجلات. لا تستخدم مفاتيح live للاختبار ولا تفتح الشراء العام.

نفّذ واختبر، ثم أعد نتائج القبول وما لم يُختبر. وجود دعم API مركزي لا يعني اكتمال واجهة أول سعودي قبل تطبيق هذه الخطوات.
